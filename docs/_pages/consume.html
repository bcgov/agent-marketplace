Install an Extension

Open the Catalogue, select an active Extension and inspect its tested install choice. Skills, instructions, prompts and agents have project-scoped manual choices for VS Code Local when their actual native files meet that client's requirements. Prompts run in Local sessions. Skills also support personal/global ~/.copilot/skills/<name>/ placement. No other global destination or third-party installer is advertised without a tested contract.

Select the source and destination

  1. Use the latest published Catalogue's full source SHA. Inspect the canonical bcgov-public/<type>/<name>, repository, path, revision, lifecycle, capabilities and checks.
  2. Download the directory at that SHA and compare its listed files with the Catalogue. A main link is latest source, may be ahead of publication, and is never a pinned or latest-published install.
  3. Inspect every mapped destination, including existing files, directories and symbolic links. Stop on a collision; another Extension or local guidance must not be overwritten.
  4. Explicitly copy the mapped native files. Preserve the skill directory/resources. Flatten the other types into the listed native file; packages needing an untested relative-resource adaptation have no choice. Do not copy the marketplace Manifest.
  5. Compare SHA-256 of each downloaded and installed file with the choice's file hashes. A URL containing a SHA or digest does not perform this comparison.

The format guide lists native paths and client evidence limits. Manual placement itself does not verify integrity; report byte verification only after the comparisons pass. A tested layout does not mean every asset was evaluated at runtime.

Update, migrate or remove

For an update, select a new published SHA, compare changes with the previously selected Catalogue and installed bytes, and explicitly replace only the mapped files. Preserve local edits for review. A legacy alias resolves to a canonical identity for lookup; use that canonical identity explicitly before placement. A Specialty transfer keeps the identity but changes the source path: inspect and explicitly approve source migration. Never follow a moved-to pointer automatically.

For removal, inspect the selected revision's exact native paths and explicitly delete only those files; preserve unrelated guidance. Non-active records have no install action. Older affected pins stay affected after quarantine/removal: review the current notice and the Operations update/removal guidance before using an old snapshot. Use its file map to remove an existing copy, without treating the old snapshot as new-install authorization.

Repository helper

Maintainers with a checkout can use the same shared choices as the site/finder. The helper downloads an immutable archive, compares the complete Catalogue inventory/digest, validates native choices, and compares copied bytes. It never executes contributed files.

uv run python scripts/find_extension.py --catalog /path/to/published-catalog.json install bcgov-public/skill/repo-hardening --project /path/to/project
uv run python scripts/find_extension.py --catalog /path/to/published-catalog.json verify bcgov-public/skill/repo-hardening --project /path/to/project
uv run python scripts/find_extension.py --catalog /path/to/published-catalog.json remove bcgov-public/skill/repo-hardening --project /path/to/project

An update uses install --previous-catalog /path/to/previous-catalog.json. A source-path/repository change also needs --allow-migration. Alias lookup needs --allow-alias or the explicit canonical identity. Every write/removal asks for confirmation; --yes records an already explicit choice. Verification needs the selected Catalogue revision and writes no local tracking files. Review locally edited files manually if comparison fails.
