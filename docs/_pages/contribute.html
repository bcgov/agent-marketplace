Contribute an Extension

Share a skill, instructions, prompt or agent. Start with Community unless a registered Specialty fits. You can create both required files and one pull request using github.com alone. No local tools are required for this browser journey.

Prefer working with an agent? Use bcgov-create-extension. For a local checkout, follow CONTRIBUTING.md.

Three authoring paths

With an agent: use bcgov-create-extension to search for an existing solution, scaffold a native package, validate, inspect the diff and request explicit consent before opening a draft PR. Locally: create the same two files, validate and push signed commits following the repository guide. In a browser: complete the starter below, then create both files in the same fork branch and one PR.

Declare actual access in the Manifest, add useful task instructions and validate before requesting review. Maintainers are contacts; editing another person's Community Extension needs human review unless the trusted-base individual maintainer eligibility is satisfied. Public bcgov membership is the automatic eligibility proxy, not proof of employment. Unknown/private membership holds for review; a public-membership 404 alone does not prove nonmembership.

All publication and automatic merge switches are currently off pending repository activation. After activation, eligible Community changes within the ten-new-identities/seven-day budget and elevated declared-risk ceiling can take the Community route only with Security-approved blockers and every required check. Exceeded or unavailable quota holds. Hard format/security failures remain failures. Specialty, non-maintainer edits, restoration and ownership changes require human review.

Specialties and onboarding

Choose Community or an active registered Specialty from the starter. Specialty owners review both native and Manifest files; the policy route is not proof that review occurred. To register a Specialty, agree scope and team coverage with Admins, add its registry entry and generated ownership in a reviewed PR, and prove reviewer delivery for both paths. Aim for at least two team members; document sole-owner coverage. See ownership procedures.

Specialties and ownership

This list and the choices above come from the Specialty registry. New Specialties require Admin-reviewed registration; registered content receives the same native-format and security validation as Community.

    Read checks and fix the branch

    Open the PR's Checks and each check's details. Format, metadata, signature and security failures require correction on the same head branch. Checks describe the exact revision; a change reruns them. Required checks still apply when automatic merging and publication are off.

    • Missing summary: add non-empty description: inside the native file's YAML frontmatter, or summary: in the Manifest. Native format requirements still apply. Quote YAML values containing a colon or other special punctuation.
    • Missing Manifest: add bcgov-extension.yaml next to the native file on its existing branch using step 2. Confirm both paths in Files changed.
    • Name unavailable: choose an unused type/name and update both paths and native name together. If you intended an edit or a Specialty transfer, edit the existing package and request human review.
    • Blocking findings: follow the reported file, field or line and correction. Remove secrets and fix undeclared access; do not add secret values to capability metadata. Read the check's safe diagnostics and rerun by committing the fix.
    • Review hold: a passing human-review route can require Specialty owners, maintainer eligibility, lifecycle review or unconfirmed membership. It is a valid review state, not an instruction to weaken checks. Read the route's reasons and request the named reviewer. With automation off, passing checks do not merge the PR.
    • Membership: Community automatic eligibility requires public membership in the bcgov GitHub organization. If membership is private or cannot be confirmed, make it public in your organization's People settings when appropriate, or ask a maintainer to review the hold. Do not provide tokens or credentials.
    • Signing: GitHub signs commits made through its web interface. Inspect each PR commit's Verified status; source commits must meet the repository's signing requirements. An unsigned local commit needs the signing recovery in the contribution guide. A green preview does not prove live signature rules or activation; Operations owners record that separately.
    • Fork run awaiting approval: ask an upstream maintainer to approve the first workflow run under the existing policy. A missing route or check is pending evidence, not a pass. Do not change repository settings to bypass it.
