# Research: A Replaceable OSS Scanner Alongside GHAS for Agent-Skill Security Checks

**Issue:** bcgov/agent-marketplace#21 ("Which replaceable OSS scanner fits agent-skill security checks alongside GHAS?"), child of #7 ("Wayfinder: v1 marketplace ready for bcgov contributors").

**Scope note:** This note is deliberately narrower than, and complements, the prior research note [`scan-extensibility-findings.md`](./scan-extensibility-findings.md) (on branch `research/scan-extensibility`), which already surveys gitleaks, semgrep generic mode, OPA/Conftest, and secondary LLM-classifier signals (Rebuff, llm-guard, promptfoo, Microsoft Prompt Shields) against a "deterministic, offline, fail-closed CI gate" bar, and separately covers GitHub Actions fork-PR hardening (`pull_request` vs `pull_request_target`). This note does **not** re-derive those findings; it cites them where relevant. New to this note: (1) precise GHAS (secret scanning + code scanning/CodeQL) capability boundaries on Markdown/YAML prose specifically, including licensing and permissions; and (2) two purpose-built, maintained OSS "agent-skill scanner" projects — NVIDIA SkillSpector and Cisco AI Defense's `skill-scanner` — that did not exist/were not evaluated in the prior note, verified here against their own repos.

---

## 1. Framing: Why GHAS Alone Is Insufficient

bcgov/agent-marketplace hosts **skills, prompts, instructions, and agent definitions** as Markdown/YAML prose submitted by contributors. GitHub Advanced Security (GHAS) — secret scanning and code scanning (CodeQL) — is already available to the repo (secret scanning and code scanning run free on public repositories, see §2.3) and should remain the first line of defense for literal credential leakage. But GHAS's two engines are purpose-built for (a) credential-shaped string detection and (b) formally-parseable source-code analysis. Neither is designed to evaluate whether a block of **natural-language instructional text** is attempting to manipulate an LLM reader (a prompt injection, a disguised "ignore previous instructions," a social-engineered capability escalation, or an obfuscated/encoded payload hidden in prose). The marketplace's threat model — adversarial PR content whose "exploit" is semantic, read by a model rather than executed by a CPU — needs an **independent, replaceable, centrally-maintained text/pattern scanner running alongside GHAS**, not a replacement for it. The catalog contract should therefore define a tool-agnostic finding format (§5) so the specific OSS scanner can be swapped without changing what "a blocking finding" means to the marketplace's CI gate.

## 2. GHAS Capabilities on Markdown/YAML Asset Files

### 2.1 Secret scanning

GitHub's own description: secret scanning "scans your entire Git history on all branches of your repository for hardcoded credentials... GitHub also automatically scans: Descriptions and comments in issues... Titles, descriptions, and comments in pull requests... Wikis..." — i.e., it operates over raw file content and several non-file PR surfaces, with no language/file-type restriction stated; Markdown/YAML plain text is scanned the same as any other committed file. (https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)

Customization layers, per the same page:
- **Generic patterns** — "Expand detection to secrets that aren't tied to a specific service provider, such as private keys, connection strings, and generic API keys."
- **Custom patterns** — "Define your own regular expressions to detect organization-specific secrets that aren't covered by default patterns."
- **Validity checks** and **AI-detected secrets** (unstructured/contextual secret detection) and **AI-generated regular expressions** (Copilot-assisted pattern authoring).
(https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)

**Custom patterns are regex-based and plain-text-oriented, not code-structure-aware:** defining one requires only a "Secret format" regular expression and an optional sample string tested via a repository-level "dry run," then "Publish pattern," with an option to additionally "Enable" **push protection** for that pattern. (https://docs.github.com/en/code-security/how-tos/secure-your-secrets/customize-leak-detection/define-custom-patterns) Custom patterns can be defined "specific to your repository, organization, or enterprise" (https://docs.github.com/en/code-security/concepts/secret-security/push-protection), i.e., GHAS does support centrally-maintained, org/enterprise-scoped custom regex rule sets, not only a single repo's own patterns — a relevant data point since the issue asks whether GHAS itself could serve the "centrally maintained custom rules" requirement for the **secret-detection** slice of this problem. However, creating/publishing a custom pattern requires repository **Settings → Security and quality** access (i.e., repo admin, or org/enterprise security-manager permissions for org/enterprise-scoped patterns) — this is an elevated, admin-gated workflow, not something a PR-time CI job configures dynamically. (https://docs.github.com/en/code-security/how-tos/secure-your-secrets/customize-leak-detection/define-custom-patterns)

**Push protection** adds a pre-receive block: "When push protection detects a potential secret during a push attempt, it will block the push... before they reach your repository," and explicitly supports blocking on **partner patterns**, **generic patterns**, **custom patterns**, and (public preview) **AI-detected generic secrets**, across push surfaces including the command line, GitHub web UI, and GitHub Desktop (coverage varies by push surface per the doc's support matrix). (https://docs.github.com/en/code-security/concepts/secret-security/push-protection)

**What custom patterns cannot do:** they are string/regex matchers against byte content, with no documented mechanism for expressing semantic judgments ("does this sentence instruct the model to exfiltrate data") — the same regex-engine limitation applies whether the target is a credential string or an attempted instruction-override phrase; a regex can catch a fixed phrase ("ignore all previous instructions") but not a paraphrase, synonym substitution, or non-English rendering of the same intent, and the docs describe no NLP/semantic layer in secret scanning's custom-pattern feature.

### 2.2 Code scanning / CodeQL and Markdown/YAML

GitHub's own CodeQL documentation lists CodeQL's full supported-language set: **C/C++, C#, Go, Java/Kotlin, JavaScript/TypeScript, Python, Ruby, Rust, Swift, and GitHub Actions workflows** — with an explicit callout: **"CodeQL does not support languages that are not listed above. This includes, but is not limited to, PHP, Scala, and others. Attempting to use CodeQL with unsupported languages may result in no alerts being generated and incomplete analysis."** (https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning) Markdown and YAML (as free-form instructional/config prose, as opposed to GitHub Actions workflow YAML, which *is* covered as its own distinct CodeQL target) are **not in this list**. This directly verifies the issue's expected answer: **CodeQL has no extractor for natural-language Markdown/YAML prose** — it builds a database by parsing a formal grammar (`"CodeQL is a programming language and associated tools that treat code like data... You generate a CodeQL database to represent your codebase... run CodeQL queries on that database"`), and prose has no such grammar to extract. (same URL)

**Third-party/Actions-based SARIF upload ("generic" code scanning use) is real and is the viable path for custom text rules — but it is GitHub's ingestion format, not an analysis engine.** GitHub's SARIF-support documentation confirms: "GitHub can parse SARIF files produced by third-party tools to display code scanning alerts in repositories" (https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support), meaning **any** external scanner — a secrets tool, a generic-pattern tool, or a purpose-built skill scanner (§3–4) — can emit SARIF 2.1.0 and have its findings rendered as native GitHub code-scanning alerts and PR annotations via the `github/codeql-action/upload-sarif` action or the `/code-scanning/sarifs` REST endpoint. This means "code scanning" as a GitHub *surface* is tool-agnostic and exactly the integration seam the issue is asking about (§5) — but GHAS itself does not supply the semantic detection logic for prose; CodeQL supplies detection only for its listed formal-grammar languages, and the "generic" SARIF-upload path is simply a transport, requiring an upstream non-GHAS tool to do the actual text analysis.

### 2.3 Licensing and permissions

Per GitHub's own "About GitHub Advanced Security" page: GHAS features split into two purchasable products — **GitHub Secret Protection** (secret scanning, push protection) and **GitHub Code Security** (code scanning/CodeQL, CodeQL CLI, Copilot Autofix, AI Scan, dependency review, security overview) — and "Some of these features, such as code scanning and secret scanning, are enabled for public repositories by default. To run the feature on your private or internal repositories, you must purchase the relevant GitHub Advanced Security product," requiring "a GitHub Team or GitHub Enterprise plan in order to purchase GitHub Code Security or GitHub Secret Protection." (https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security) Since bcgov/agent-marketplace is a public repository, both secret scanning and code scanning are available at no additional license cost today; this would change if the catalog or its workflows were ever moved to a private/internal repository, which is the licensing argument for not hard-coupling the catalog's security gate to GHAS-only tooling.

Configuring custom secret-scanning patterns, enabling push protection for a pattern, and managing org/enterprise-level pattern scope all require elevated permissions (repository **Settings → Security and quality** admin access at minimum, or org/enterprise security-manager role for broader scope) — i.e., these are not self-service changes a contributor or even a repo-write collaborator can make per PR; only a smaller set of org/repo admins can expand GHAS's own coverage. (https://docs.github.com/en/code-security/how-tos/secure-your-secrets/customize-leak-detection/define-custom-patterns; https://docs.github.com/en/code-security/concepts/secret-security/push-protection)

### 2.4 Explicit answer: does GHAS evaluate natural-language instructional content for prompt-injection / malicious intent?

**No.** Nothing in GitHub's own secret-scanning or code-scanning documentation describes a semantic content-moderation or intent-classification capability. Secret scanning's "AI-detected secrets" feature (https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning) uses AI specifically to find **unstructured secrets like passwords** by surrounding-code-context heuristics — it is still scoped to credential detection, not general malicious-instruction detection. Code scanning's CodeQL engine requires a formally-parseable language database and explicitly excludes anything not in its fixed language list (§2.2), so it cannot analyze Markdown/YAML prose at all, semantically or otherwise. GHAS therefore provides **no documented coverage for prompt-injection or malicious natural-language instructional content** — it is a secrets/code-pattern-focused product family, not a content-moderation or semantic-safety product, which is precisely why the marketplace needs an independent, purpose-chosen OSS layer alongside it.

### 4.3 NVIDIA SkillSpector

**What it is:** "**Security scanner for AI agent skills.** Detect vulnerabilities, malicious patterns, and security risks before installing agent skills," built as a LangGraph workflow with CLI, Docker, and MCP-tool entry points, and positioned as part of "the NVIDIA Verified Skills pipeline, which scans, evaluates, and signs agent skills before publication" for the NVIDIA skills catalog. (https://github.com/NVIDIA/SkillSpector)

**License:** Apache License 2.0, confirmed via repository license badge and GitHub API (`"license": {"spdx_id": "Apache-2.0"}`). (https://github.com/NVIDIA/SkillSpector; `api.github.com/repos/NVIDIA/SkillSpector`)

**Maintenance:** Created 2026-03-21; most recent commit and release checked at research time (2026-10-30) were same-day/within days (`v2.13.2` released 2026-10-28; commit `9adb1a6` on 2026-10-30), i.e., actively maintained with a regular release cadence. (`api.github.com/repos/NVIDIA/SkillSpector/releases`, `/commits`)

**Detection approach:** "71 vulnerability patterns across 17 categories: prompt injection, data exfiltration, privilege escalation, supply chain, excessive agency, output handling, system prompt leakage, memory poisoning, tool misuse, rogue agent, anti-refusal, trigger abuse, dangerous code (AST), taint tracking, YARA signatures, MCP least privilege, and MCP tool poisoning," run as "Two-stage analysis: Fast static analysis + optional LLM semantic evaluation." (https://github.com/NVIDIA/SkillSpector)

**Offline/deterministic operation:** The static stage is runnable fully locally and deterministically via `--no-llm` ("Static-only scan of a local skill (no API key required): `skillspector scan ./my-skill/ --no-llm`"), including a Dockerized no-Python-required path. (https://github.com/NVIDIA/SkillSpector; https://owasp.github.io/www-project-agentic-skills-top-10/skill-scanner-integration) However, one static sub-analyzer ("SC4") "queries OSV.dev for real-time CVE data with automatic offline fallback" — meaning a fully network-isolated run depends on graceful fallback behavior for that one component rather than being network-free by architecture, and the optional LLM semantic stage requires an external or local model provider (`SKILLSPECTOR_PROVIDER` env var: `openai`, `anthropic`, `bedrock`, `ollama`, etc.) and is explicitly non-deterministic. (`docs/DEVELOPMENT.md`, https://github.com/NVIDIA/SkillSpector)

**Custom rules / centrally maintained rule packs:** Findings can be suppressed via a "Baseline / false-positive suppression" mechanism (glob-rule or fingerprint baseline, documented in `docs/SUPPRESSION.md`), but the README does not document a first-class external "rule-pack repository" format analogous to gitleaks' `.gitleaks.toml` or semgrep's standalone rule YAML files; the 71 built-in patterns appear to ship with the tool itself rather than as a separately versioned, swappable ruleset. (https://github.com/NVIDIA/SkillSpector)

**Structured output:** `--format sarif --output report.sarif` emits "SARIF 2.1.0" directly, confirmed usable in a GitHub Actions workflow uploading via `github/codeql-action/upload-sarif@v3` to surface findings in the Security → Code scanning tab. (https://github.com/NVIDIA/SkillSpector; https://owasp.github.io/www-project-agentic-skills-top-10/skill-scanner-integration)

**Honest limitation, in the project's own words:** the README states the motivating dataset finding ("26.1% of skills contain vulnerabilities and 5.2% show likely malicious intent" across "31,132-skill analyzed subset") as a detection *rate*, not a completeness claim, and frames the tool's purpose as helping answer "Is this skill safe to install?" — a question the tool informs but does not conclusively answer, especially in `--no-llm` static-only mode where recall is necessarily lower than the two-stage pipeline with LLM semantic analysis enabled. (https://github.com/NVIDIA/SkillSpector)

### 4.4 Cisco AI Defense `skill-scanner`

**What it is:** "A best-effort security scanner for AI Agent Skills that detects prompt injection, data exfiltration, and malicious code patterns," combining "pattern-based detection (YAML + YARA-X), AST and dataflow analysis, an optional LLM-as-a-judge, and a bounded CEL decision layer over typed detector facts," supporting the OpenAI Codex Skills and Cursor Agent Skills formats per the Agent Skills specification, plus (with `--lenient`) Claude Code-style flat Markdown skill repos. (https://github.com/cisco-ai-defense/skill-scanner)

**License:** Apache License 2.0 — confirmed directly from the repository's `LICENSE` file text ("Apache License, Version 2.0... Copyright 2026 Cisco Systems, Inc. and its affiliates"), despite GitHub's API license-detector misreporting it as `NOASSERTION`/"Other" (a known GitHub license-detection limitation, not evidence of a non-OSS license). (https://raw.githubusercontent.com/cisco-ai-defense/skill-scanner/main/LICENSE)

**Maintenance:** Created 2026-01-29; most recent commit (`f782465`, 2026-10-26) and release (`2.3.2`, 2026-10-26) checked at research time were within the current week, with a visible CI badge (`python-tests.yml`) indicating an active test suite. (`api.github.com/repos/cisco-ai-defense/skill-scanner`; https://github.com/cisco-ai-defense/skill-scanner)

**Offline/deterministic operation:** The README is explicit that the rule/YARA-X + AST/dataflow layer is the deterministic, local detection tier, separate from "an optional LLM-as-a-judge" and "optional cloud services" tiers — i.e., the architecture is explicitly layered to let an adopter run only the local/deterministic tier. The package also ships a **pre-commit hook** integration for local, pre-push scanning. (https://github.com/cisco-ai-defense/skill-scanner)

**Custom rules / centrally maintained rule packs:** This is the strongest-documented candidate for the issue's "centrally maintained custom rules" requirement among the two purpose-built scanners. A dedicated **scan-policy YAML** system lets an adopter "Generate a policy file from a preset, then customise it" (`skill-scanner generate-policy --preset low-noise -o my_policy.yaml`) with explicit deep-merge semantics over the package's own `default_policy.yaml` ("Custom policies merge on top of defaults — you only need to include the sections you want to override... Omitted sections inherit from the defaults"), plus five named built-in presets (`strict`, `balanced`, `permissive`, `low-noise`, `quiet`) each with **published, measured** false-positive-rate/F1 tradeoffs rather than marketing claims. The policy file is a standalone YAML artifact that an organization can own and version in its own repository, independent of the `skill-scanner` package release cycle. (https://cisco-ai-defense.github.io/docs/skill-scanner/recommended-settings; raw `docs/user-guide/custom-policy-configuration.md`)

**Structured output:** "SARIF output for GitHub Code Scanning" is listed as a top-level highlight, alongside a documented "reusable GitHub Actions workflow" and "exit codes for build failures" for CI gating. (https://github.com/cisco-ai-defense/skill-scanner)

**Honest limitation, in the project's own words — the most explicit of any tool surveyed in either research note:** under a README section titled "Scope and Limitations": *"Skill Scanner is a detection tool. It identifies known and probable risk patterns, but it does not certify security."* Specifically: *"No findings ≠ no risk... A scan that returns 'No findings' indicates that no known threat patterns were detected. It does not guarantee that a skill is secure, benign, or free of vulnerabilities,"* and *"Coverage is inherently incomplete... no automated tool can detect every technique, especially novel or zero-day attacks,"* and *"Human review remains essential. Automated scanning is one component of a defense-in-depth strategy."* Its own published benchmark against "MaliciousSkillBench" states: **"Rules alone catch 7.7% of malicious skills at HIGH, at a 4.0% false-positive rate,"** rising to "66.7% reach review at MEDIUM+ (15.4% FPR)" only once the (non-deterministic, opt-in) LLM judge is enabled. (https://github.com/cisco-ai-defense/skill-scanner)

## 5. Minimal, Tool-Agnostic Integration Boundary (Description Only — No Implementation)

To keep the marketplace's CI gate decoupled from any single scanner's native output format, the gate should be defined against a small, stable **normalized "marketplace finding" schema**, with every candidate scanner's native output (gitleaks JSON/SARIF, semgrep JSON/SARIF, SkillSpector SARIF, `skill-scanner` SARIF) mapped into it before the policy layer evaluates pass/fail. The schema needs, at minimum:

- **`severity`** — a small closed enum (e.g., `critical`/`high`/`medium`/`low`/`advisory`), independent of any one tool's own severity vocabulary, so rule authors and reviewers read one consistent scale regardless of which scanner produced a finding.
- **`rule_id`** — a stable identifier for the specific rule/pattern that fired, qualified by the producing tool (e.g., `tool:rule-id`) so the same semantic rule name from two different tools is never silently conflated, and so a rule's history/rationale can be traced across rule-pack versions.
- **`location`** — the asset's file/path and, where meaningful (line-addressable prose/YAML), a line or line-range; for non-line-addressable findings (e.g., a whole-asset risk score), the asset path alone is sufficient, matching SARIF's own `physicalLocation` concept for GitHub's PR-diff annotation support (§5.1 below).
- **`message`** — a short, human-readable description of what was detected and why it's flagged (no model-generated or non-deterministic reformulation inside the blocking schema itself — the message should reflect the deterministic layer's own rule text).
- **`category`** — a closed taxonomy slot (e.g., `secret`, `injection-pattern`, `obfuscation`, `policy-violation`, `capability-declaration-mismatch`) so the downstream policy layer (OPA/Conftest, per the prior note) can express rules per-category rather than per-tool.
- **`tool_name` + `tool_version` / `ruleset_version`** — which scanner and which version of its engine *and* its rule pack produced the finding, both independently versioned, so a later audit can reproduce exactly what ran and know whether a finding is attributable to an engine change or a rule-pack change.
- **A `disposition` field distinguishing `blocking` vs `advisory`** — this is the single most important boundary established in both this note and the prior note's final recommendation: a **blocking/fail-closed** finding must be fully deterministic (reproducible, same bytes → same finding, every run) — e.g., a known-secret regex match, a banned literal construct, or a pattern a human/CODEOWNER has pre-approved as always-block; an **advisory** finding is anything produced by a heuristic, a score/confidence threshold, or any non-deterministic (LLM-based) analysis stage, including SkillSpector's and `skill-scanner`'s own optional LLM-judge tiers (§4.3–4.4) and any secondary classifier signal already set aside as advisory-only in the prior note's §3.4. Advisory findings should never, by themselves, fail a required status check; they should be surfaced for human CODEOWNER review (e.g., as a PR comment or non-blocking check annotation).

### 5.1 Why SARIF is the natural common interchange format

GitHub's own SARIF-support documentation confirms code scanning is designed to ingest **any** conformant SARIF 2.1.0 file, not just CodeQL's own output: "GitHub can parse SARIF files produced by third-party tools to display code scanning alerts in repositories." (https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support) All four OSS candidates surveyed in this note (gitleaks, semgrep, SkillSpector, `skill-scanner`) natively emit SARIF (§3), and SARIF's own `reportingDescriptor`/`rule` vs. `result` structure maps cleanly onto the normalized schema above (`rule_id` ↔ SARIF `ruleId`, `location` ↔ SARIF `physicalLocation`, `tool_name`/`tool_version` ↔ SARIF `toolComponent`). GitHub's docs further note the specific conditions under which an alert renders as an **inline PR-diff annotation** rather than only a repository-level alert: "For display in a pull request check, an alert must meet all the following conditions: All the lines of code identified by the alert exist in the pull request diff... The alert must exist in the lines of code added or edited in the pull request" (https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support) — a concrete reason to populate `physicalLocation`/line ranges whenever a finding is line-addressable, and a concrete reason the normalized schema's `location` field should carry line information when available. Using SARIF as the interchange format lets the marketplace's CI gate consume findings from gitleaks *or* semgrep *or* SkillSpector *or* `skill-scanner` *or* a future replacement through one ingestion path, with the scanner-specific mapping logic isolated to a single small adapter per tool rather than baked into the policy/gating logic itself — directly satisfying the issue's "replaceable without coupling the catalog contract to one vendor/tool" requirement.

## 6. Final Recommendation

**Keep GHAS enabled as-is** (it is free on this public repo per §2.3, and correctly covers literal credential leakage across the whole repository, issues, PRs, and wikis — a surface broader than any PR-scoped CI job can reach) **and add an independent, replaceable OSS layer for the semantic/text-pattern problem GHAS does not address.** Consistent with the prior note's three-layer recommendation (signature scanner → pattern/structural scanner → policy engine), this note's incremental finding is that a **fourth, purpose-built layer is now a credible, actively-maintained option**: a dedicated agent-skill scanner (SkillSpector or `skill-scanner`) run in its **static-only, `--no-llm`/no-LLM-judge mode** as an additional **blocking** signal alongside gitleaks/semgrep, with its optional LLM-based semantic tier wired in only as a **non-blocking, advisory** signal (per the `disposition` field in §5).

**Recommended combination (no single tool is a silver bullet):**
1. **gitleaks** (MIT) — blocking secret/credential detection, locally-vendored config.
2. **semgrep generic mode** (LGPL-2.1), locally-vendored custom rules only (no registry pull) — blocking structural/multi-line pattern detection beyond plain regex.
3. **One purpose-built agent-skill scanner** — either **NVIDIA SkillSpector** (Apache-2.0) or **Cisco AI Defense `skill-scanner`** (Apache-2.0), run with its static/deterministic tier only (`--no-llm` / no LLM judge) as an additional **blocking** signal, chosen based on which tool's rule-governance model (`skill-scanner`'s versioned, mergeable policy-YAML system is, per §4.4, the more clearly documented fit for "centrally maintained custom rules separate from the scanner binary") better matches bcgov's desired rule-ownership workflow. Both tools' optional LLM-semantic stage, if enabled at all, must be wired as **advisory-only**, exactly like the secondary classifier signals already set aside in the prior note's §3.4.
4. **OPA/Conftest** (Apache-2.0) — the policy/gating layer, unchanged from the prior note's recommendation, now consuming a normalized finding set (§5) assembled from all of the above via SARIF.

**All findings flow through the normalized schema (§5) with an explicit `blocking`/`advisory` split, and SARIF (§5.1) is the common interchange format** linking every scanner's native output to GitHub's code-scanning surface and to the policy layer's own structured input — so any one tool (including GHAS's own third-party-SARIF path, should bcgov ever choose to route findings through it) can be swapped without changing the catalog's contract about what a blocking finding *means*.

### Caveats — nothing proves safety

Every primary source consulted in this note that discusses its own limitations says, in its own words, the same thing: **no static or regex-based tool proves a skill, prompt, or agent definition is safe.** Semgrep's own docs warn generic-mode "quality... can vary" and show a trivial encoding bypass (§2.2/prior note §3.2). SkillSpector frames its own headline statistic as a detection rate on a benchmark, not a completeness guarantee (§4.3). Cisco's `skill-scanner` states this most explicitly of any tool surveyed across both notes: *"No findings ≠ no risk... it does not certify security... Human review remains essential,"* backed by its own published benchmark showing rules-only detection catching only **7.7%** of known-malicious skills at HIGH confidence (§3, §4.4). GHAS itself has no documented capability for this threat class at all (§2.4). The correct posture for bcgov/agent-marketplace is therefore: a deterministic, replaceable, multi-layer **blocking** gate that catches what it can reliably catch (secrets, known-bad literal/structural patterns, declared-capability policy violations) without over-claiming completeness; any semantic/heuristic signal (whether a dedicated scanner's optional LLM tier or a separate classifier) is surfaced as **advisory** input to human CODEOWNER review, never as the sole basis for a merge decision, and the catalog's provenance/review process (already required per `CONTRIBUTING.md`) remains the backstop no automated tool replaces.
