# Research: Scanning Repository-Hosted Agent Assets (Prose/Markdown) for Malicious Content — Methodologies and Tool Candidates

## 1. Framing the Problem

bcgov/agent-marketplace is a catalog of **AI agent assets** — skills, prompts, instructions, and agent definitions expressed as Markdown and YAML prose — submitted via pull request and a federated candidate-issue intake process. This is structurally different from classic dependency/package scanning (e.g., `npm audit`, Dependabot, Trivy), which inspects **compiled artifacts and manifests with known identities** (a package name + version resolves to a CVE database entry) or **source code with a formal grammar** (so an AST-based tool can reason about control flow, taint, and data flow). Agent assets have neither: they are unstructured or semi-structured natural-language documents whose "payload" is an instruction an LLM will later read and (potentially) obey. The attack surface is therefore closer to **free-text content moderation / secret-scanning** than to **software-composition analysis**: the question is not "does this dependency have a known vulnerable version" but "does this prose contain a pattern — an injected instruction, an obfuscated encoding, a credential, or a dangerous capability claim — that a human reviewer, and a deterministic no-network CI gate, should flag before merge." This is why bcgov's existing scanner is deliberately described in repo docs as a **"deterministic security policy"** that **"fails closed"** and produces versioned **"policy output"** — the goal is a reproducible, auditable gate, not a best-effort content classifier. The research below surveys five methodology families against that requirement, using the tools' own primary documentation.

## 2. Comparison Table

| | 1. Deterministic rules / allow-deny lists | 2. Signature/pattern databases (regex/string) — gitleaks, trufflehog | 3. Parser/AST static analysis — semgrep | 4. Policy engines — OPA/Rego, Conftest | 5. Classifier/LLM-based signals (secondary only) — Prompt Shields, Rebuff, llm-guard, promptfoo |
|---|---|---|---|---|---|
| **Pros for this use case** | Simplest, fully explainable; ideal for exact-match blocklists (known-bad domains, banned function names, required frontmatter fields) | Purpose-built for scanning **any byte stream** (not just code) for credential-shaped strings; mature entropy + regex rule packs; proven in CI gates for years | Can run in a **generic/text pattern mode** (not just AST mode) over non-code files, giving structured multi-line pattern matching beyond plain regex, with a large existing rule ecosystem | Excellent for expressing **pass/fail policy over structured JSON** (e.g., the *scanner's own findings*, asset manifest/frontmatter fields, declared capabilities) as data, separate from the detection logic itself | Can catch semantic/novel prompt-injection phrasing that no regex anticipated; useful as an advisory, non-blocking signal surfaced to human reviewers |
| **Cons for this use case** | Brittle/incomplete alone; combinatorial explosion of bypass variants (unicode homoglyphs, synonyms) not caught by exact lists | Regexes don't understand nested obfuscation (zero-width chars, base64-wrapped instructions) unless explicitly engineered for it; no semantic understanding of "instruction" vs "description" | Generic mode is explicitly documented as **lower-quality/inconsistent** outside code, tokenizes only on ASCII word boundaries, can't decode entities/escapes, limited metavariable semantics | Does not itself *detect* patterns in raw prose — needs an upstream extractor to turn Markdown/YAML into structured input; Rego is not a prose-scanning language | Non-deterministic (model sampling), network-dependent (cloud APIs) or heavy local ML models, cost/latency, cannot be a required fail-closed CI gate; several listed tools are prototypes or archived |
| **Determinism** | Fully deterministic | Fully deterministic (regex/entropy, no model) | Fully deterministic (no LLM; AST/token matching is a pure function of input + ruleset version) | Fully deterministic (Rego evaluation is a pure function of input + policy) | Non-deterministic where LLM-based (Prompt Shields, Rebuff's LLM layer, llm-guard's ML-based PromptInjection scanner); deterministic only for their non-ML sub-components (e.g., llm-guard's regex-based `Secrets`/`BanSubstrings` scanners) |
| **Offline capability** | Yes — trivially, since it's just code/data you own | Yes — gitleaks and trufflehog are self-contained binaries with built-in rule packs; no network call required for the default config | Partial — the OSS CLI engine runs fully locally, but pulling rules from the **Semgrep Registry** requires network access and reports metrics to Semgrep's server by default; **local/custom rule files avoid both** | Yes — `opa eval` / `conftest test` are local binaries evaluating local Rego files against local input; no network dependency | No / exclusionary for primary gate — Microsoft Prompt Shields is an **Azure cloud API only** (no self-hosted/offline option); Rebuff's `RebuffSdk` requires OpenAI + Pinecone API keys; llm-guard can run local ML models but is now **archived/unmaintained**; promptfoo's red-team evaluation is designed as an **offline testbed** against a target LLM, not a blocking CI gate for static asset review |

**Why pure AST/code-parsing is a poor primary fit for prose:** Semgrep's own documentation states generic pattern mode exists specifically "for languages that do not have a parser" and that "the generic mode works fine with any human-readable text... as long as it is primarily based on ASCII symbols," but explicitly warns "the quality of results in the generic mode can vary" and that encoded/obfuscated text (its own example: XML numeric-character-reference encoding of `Hello`) defeats it because the tool has no semantic understanding of the underlying language — there is no grammar for "English instructional prose" the way there is for Python or JavaScript. AST-based code analysis fundamentally assumes a formal, parseable grammar with defined tokens, scopes, and control flow; Markdown/YAML instructional text has none of that, so a code-AST tool's core value proposition (precise structural matching, taint tracking) does not transfer.

**Why cloud LLM-classifier APIs are excluded as primary gates:** Microsoft's own Prompt Shields documentation describes it strictly as an **Azure AI Content Safety** API service returning `detected`/`filtered` annotations — there is no documented self-hosted or offline deployment option, meaning every scan call is a network dependency on a third-party cloud service, which conflicts with a "no-network" deterministic policy requirement; it is also explicitly a classifier ("Prompt Shields detect attempts to manipulate model behavior... They don't determine whether content is harmful [or] factually accurate"), i.e., probabilistic, not a deterministic pass/fail rule. Combined with latency/cost per call and the requirement to send repository PR content to an external vendor, this rules it out as a required fail-closed gate, though it (and similar classifiers) can remain a secondary advisory signal.

## 3. Deep-Dive Per Tool

### 3.1 gitleaks

**What it is:** A Go CLI "for **detecting** secrets like passwords, API keys, and tokens in git repos, files, and whatever else you wanna throw at it via `stdin`," built on a regex + entropy detection engine ("Regex is (almost) all you need" per its own linked blog post). (https://github.com/gitleaks/gitleaks)

**License:** MIT License, Copyright (c) 2019 Zachary Rice. (https://raw.githubusercontent.com/gitleaks/gitleaks/master/LICENSE)

**Offline/local capability:** Fully local. The README documents a `--config` precedence chain (CLI flag → `GITLEAKS_CONFIG` env var → `GITLEAKS_CONFIG_TOML` inline content → `.gitleaks.toml` in target path → built-in default config), all of which are local file/env resolutions with **no network call required**; the default ruleset is compiled into the binary (referenced at `https://github.com/gitleaks/gitleaks/blob/master/config/gitleaks.toml`, fetched locally or bundled, not queried at runtime). (https://github.com/gitleaks/gitleaks)

**Rule maintenance:** Built-in default TOML rule pack (`config/gitleaks.toml`) maintained in the gitleaks repo itself; users can `extend` (append/override) the default config or supply a fully custom one, and configs can be chained to a depth of 2. The project's README currently carries a maintainer notice: "Gitleaks is feature complete... Future releases will be security patches only," with the maintainer shifting focus to a successor project "Betterleaks" — a relevant maintenance-trajectory caveat for long-term rule-pack freshness. (https://github.com/gitleaks/gitleaks)

**Determinism:** Fully deterministic — regex/entropy matching, no ML component documented.

**Fail-closed CI gate suitability:** Strong fit. CLI exposes `--exit-code int` ("exit code when leaks have been encountered", default `1`) and `-f/--report-format` supporting `json, csv, junit, sarif, template` — i.e., machine-readable SARIF/JSON output plus a controllable non-zero exit code, exactly the shape needed for a required, binary pass/fail GitHub Actions check. It also supports a `--baseline-path` mechanism to suppress previously-accepted findings, useful for incremental adoption without re-litigating historical content. (https://github.com/gitleaks/gitleaks)

*(Comparator noted but not deep-dived: TruffleHog, Apache-2.0-badged per its README, additionally performs **live credential verification** against provider APIs ("Found verified result... Detector Type: AWS... Verified":true), which is a deliberate network call per finding and thus a partial exception to "no-network" if verification is enabled — relevant if bcgov ever adopts it alongside/instead of gitleaks. https://github.com/trufflesecurity/trufflehog)*

### 3.2 semgrep

**What it is:** A static-analysis engine that matches **patterns** against code. For natively supported languages it parses a real AST; for everything else it offers an explicit **"generic" pattern-matching mode** that treats a document as "a nested sequence of ASCII words, ASCII punctuation, and other bytes" using indentation and brace nesting as structural cues, with an ellipsis operator (`...`) and single-word metavariables (`$X`). (https://docs.semgrep.dev/writing-rules/generic-pattern-matching, redirected from https://semgrep.dev/docs/writing-rules/generic-pattern-matching)

**License:** LGPL-2.1 (per the `develop` branch LICENSE file). (https://raw.githubusercontent.com/semgrep/semgrep/develop/LICENSE)

**Offline/local capability:** Partial, rule-source-dependent. The CLI reference documents: "By default, Semgrep will report pseudonymous usage metrics to its server **if you pull your configuration from the Semgrep registry**... To modify this behavior, see the `--metrics` option." This confirms that (a) registry-sourced rulesets imply a network dependency and telemetry by default, and (b) **locally authored/vendored rule files avoid both** the registry fetch and the metrics call, letting the core matching engine run fully offline. There is also an `--enable-version-check` flag ("Checks Semgrep servers to see if the latest version is run"), a further optional network touch-point that can be disabled. (https://docs.semgrep.dev/cli-reference, redirected from https://semgrep.dev/docs/cli-reference)

**Rule maintenance:** Two models documented — (1) the hosted **Semgrep Registry**, a community/vendor rule-pack ecosystem pulled over the network at scan time, and (2) locally maintained YAML rule files (`rules:` with `id`, `pattern`, `languages`, `severity`, `message`, `metadata`) versioned like any other repo artifact — the generic-mode example rule in the docs shows this exact structure (`languages: [generic]`, `paths.include` globs). For a no-network policy, bcgov would maintain its own versioned rule file(s) rather than pulling the registry. (https://docs.semgrep.dev/writing-rules/generic-pattern-matching)

**Determinism:** Fully deterministic — pattern/AST matching is a pure function of input + rule file + engine version; no model sampling involved in the open-source matching engine itself.

**Caveats specific to prose (direct from docs):** "The generic mode works fine with any human-readable text, as long as it is primarily based on ASCII symbols. Since the generic mode does not understand the syntax of the language you are scanning, the quality of the result may differ from language to language... it's possible or even easy to write code in weird ways that prevent generic mode from matching." The docs give a concrete obfuscation-defeats-matching example: XML numeric character references (`&#x48;&#x65;&#x6C;&#x6C;&#x6F`) are not resolved to `Hello`, so a literal-text rule misses the encoded form entirely — directly relevant to bcgov's concern about base64/hex/unicode smuggling, since semgrep's generic mode **will not decode these by itself**; it only matches what's literally present in the byte stream unless a rule is specifically written to catch encoding markers (e.g., flag the presence of a base64-looking blob, not its decoded content). Metavariables in generic mode are also restricted to matching a single `[A-Za-z0-9_]+` token and cannot span multi-word phrases, and the ellipsis operator is capped at ~10 lines (documented pitfall: "If the pattern commonly matches many lines, use `... ...`"). (https://docs.semgrep.dev/writing-rules/generic-pattern-matching)

**Fail-closed CI gate suitability:** Good, with caveats. The CLI reference documents an `--error` flag: "Exit 1 if there are findings. Useful for CI and scripts," giving a deterministic exit-code gate; SARIF and JSON output formats are part of the broader Semgrep ecosystem (used for GitHub code scanning integration) though the specific SARIF flag wasn't re-verified in the excerpt fetched here beyond the exit-code behavior. Net assessment: viable as a **secondary layer** (structured multi-line pattern matching beyond simple regex) run with locally vendored rules and `--error`, but its own documentation concedes it is not purpose-built for prose and is weaker than a dedicated secrets/obfuscation scanner for that specific sub-problem.

### 3.3 OPA / Rego + Conftest

**What they are:** Open Policy Agent (OPA) is "an open source, general-purpose policy engine" using the declarative language **Rego** to evaluate structured `input` (JSON) against policy and emit decisions, including arbitrary structured output, not just allow/deny booleans. (https://www.openpolicyagent.org/docs) Conftest is a CLI utility built directly on OPA/Rego: "Conftest is a utility to help you write tests against structured configuration data... Conftest relies on the Rego language from Open Policy Agent for writing policies." (https://www.conftest.dev/)

**License:** OPA is Apache License 2.0 (per its repo LICENSE). (https://raw.githubusercontent.com/open-policy-agent/opa/main/LICENSE) Conftest is also Apache License 2.0, "Copyright (C) 2019 Gareth Rushgrove." (https://raw.githubusercontent.com/open-policy-agent/conftest/master/LICENSE)

**Offline/local capability:** Fully local. Conftest's documented usage pattern is `conftest test deployment.yaml` or piping via stdin (`cat deployment.yaml | conftest test -`), evaluating a local `policy/*.rego` directory against a local input file — no network call is part of the documented core workflow. (https://www.conftest.dev/)

**Rule maintenance:** Policy-as-code. Conftest looks for `deny`, `violation`, and `warn` rules (optionally suffixed, e.g. `deny_myrule`) inside a `main` namespace by default (overridable via `--namespace`/`--all-namespaces`); rules are plain `.rego` files checked into the repo like source code, so versioning/review happens through normal git history and PR review — there is no external "registry" dependency analogous to Semgrep's. Conftest also supports rich **metadata** output: a rule can return a structured object (`{"msg": ..., "metadata_abc": 123, ...}`) rather than a bare string, and supports a documented `_loc` field (added in Conftest v0.64) to attribute a violation to a specific `file`/`line`, which is directly useful for pointing a policy failure back at the exact asset file and line that triggered it. (https://www.conftest.dev/)

**Determinism:** Fully deterministic — Rego evaluation is a pure function of the policy and the `input` document; no model involved.

**Fail-closed CI gate suitability:** Excellent **for the orchestration/gating layer**, not for raw prose detection. Conftest's own example shows exactly the fail-closed shape bcgov wants: `conftest test deployment.yaml` → `FAIL - deployment.yaml - <reason>` with a summary line (`2 tests, 0 passed, 0 warnings, 2 failures, 0 exceptions`) and a documented `--output json` mode producing a structured `{"filename":..., "failures":[{"msg":...,"metadata":{...}}]}` array — ideal as the **policy layer that consumes the JSON findings emitted by gitleaks/semgrep/custom scanners** and renders the final binary "deny" decision, keeping detection logic (regex/pattern rules) separate from policy logic (what counts as a blocking violation, what's an allow-listed exception, what requires CODEOWNER override). This matches bcgov's own stated architecture of a distinct "deterministic security policy" producing "policy output" separate from "scanner findings." Important limitation confirmed from docs: Conftest's supported input formats are structured-data formats (YAML, JSON, TOML, HCL, Dockerfile, INI, XML, etc.) — it is **not** a prose/text scanner itself, so Markdown prose content would need to be pre-extracted into structured fields (e.g., YAML frontmatter, or a JSON object produced by an upstream extraction step) before Rego policy can reason over it. (https://www.conftest.dev/)

### 3.4 Optional/Secondary Classifier Signals — Rebuff, llm-guard, promptfoo, Microsoft Prompt Shields

These are explicitly investigated as **non-primary, advisory-only** signals per the task's framing, and the primary-source evidence strongly supports keeping them out of a required fail-closed gate:

- **Microsoft Prompt Shields** (Azure AI Content Safety): A cloud classification API that "detect[s] attempts to manipulate your model's behavior through adversarial inputs," scanning `user prompt` and `documents` content for "user prompt attacks" and "document attacks" (the latter specifically "hidden instructions embedded in document content... that try to hijack the model session" — directly analogous to the bcgov threat model). Its own docs state plainly: "Azure AI Content Safety doesn't independently verify the submitted content's provenance" and "Prompt Shields detect attempts to manipulate model behavior... They don't determine whether content is harmful, factually accurate... or aligned with the application's task." There is no documented offline/self-hosted deployment — it is accessed only as an Azure API, meaning every scan is a network call to a third-party cloud service with attendant cost, latency, and data-exposure implications, and the underlying detection is a trained classifier (non-deterministic in the sense of model-version-dependent behavior, not a versioned static rule file). Explicitly excluded as a primary gate. (https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection)

- **Rebuff**: Described by its own README as a "**prototype**" that "cannot provide 100% protection against prompt injection attacks," offering four layers of defense — heuristics, **LLM-based detection** (a dedicated LLM call), a **VectorDB** of prior attack embeddings, and canary tokens. Its primary `RebuffSdk` usage example requires an `openai_apikey` and a `pinecone_apikey`/index as constructor arguments — i.e., two external cloud API dependencies are baked into the basic getting-started usage. Self-hosting still requires standing up Supabase + a vector DB (Pinecone or Chroma) and an OpenAI key. A "Local-only mode" appears only on Rebuff's own **roadmap** (not yet shipped per the README at time of fetch), confirming full offline operation is not currently available from primary sources. Non-deterministic (LLM-based layer) and explicitly a prototype — unsuitable as a required gate. (https://github.com/protectai/rebuff)

- **llm-guard**: MIT-licensed Python toolkit (badge confirmed: "MIT license") offering modular `input_scanners`/`output_scanners`, several of which are directly relevant and **can** run as local, deterministic components — e.g., `BanSubstrings`, `Regex`, `Secrets`, and notably `InvisibleText` (a scanner explicitly named for invisible/zero-width-character detection) — while others (`PromptInjection`, `Toxicity`, `BanTopics`) are implemented as local ML/transformer classifiers (non-deterministic relative to a fixed-rule gate, though they run offline once model weights are downloaded, avoiding a live network call per scan). Critically, the repo's own README carries a project-level warning banner: **"THIS PROJECT HAS BEEN ARCHIVED... no longer under active development or maintained"** — a significant negative finding for long-term adoption as infrastructure. (https://github.com/protectai/llm-guard)

- **promptfoo**: Positions itself explicitly as an **LLM red-teaming / evaluation framework** — "LLM red teaming is a way to find vulnerabilities in AI systems *before* they're deployed by using simulated adversarial inputs," run in "offline testbeds" as part of a development cycle, sometimes integrated "into processes like CI/CD." MIT-licensed (per its repo LICENSE file). This is architecturally a different tool from a static-asset scanner: it generates adversarial probes and evaluates a *target model's responses*, not a static classifier over a submitted document — relevant to bcgov only as an optional way to red-team an *agent's behavior* post-merge, not to gate the raw prose content of a submitted skill/prompt file. (https://www.promptfoo.dev/docs/red-team/; https://raw.githubusercontent.com/promptfoo/promptfoo/main/LICENSE)

**Overall assessment for category 5:** None of these four tools, as documented by their own primary sources, meet the "offline, deterministic, fail-closed CI gate" bar. They are appropriately scoped as **secondary, advisory signals** surfaced to human CODEOWNER reviewers (e.g., "this classifier flagged possible injected instructions, please review manually") rather than inputs to the deterministic policy decision itself.

## 4. GitHub Actions Safety for Untrusted PR Content

**Core question:** Can a `pull_request` (not `pull_request_target`) workflow safely run a scanner over fork PR content with no secrets exposed?

**Yes, and this is exactly the mechanism GitHub's own hardening docs describe as the safe default.** From GitHub's dedicated "Securely using `pull_request_target`" guide:

> "The `pull_request` event (along with `pull_request_review` and `pull_request_review_comment`) is unusual: it runs the workflow file from the **merge commit of the pull request**. For a pull request opened from a fork, that commit is controlled by someone without write access to the base repository. To run untrusted workflow code safely, GitHub restricts these events to a **read-only `GITHUB_TOKEN`**, **withholds access to other secrets**, and applies fork approval policies to prevent compute abuse. By default, `actions/checkout` in a `pull_request` workflow also checks out the pull request's merge commit, so the code checked out and the workflow that runs are consistent."

This is the precise primary-source confirmation requested: fork-originated `pull_request` workflows get a read-only token and no repository secrets by default, which is why a `pull_request`-triggered scanner job (checking out the PR's own merge commit, running gitleaks/semgrep/conftest, and failing the check) is safe even for anonymous or low-trust contributors — there is nothing of value for a malicious PR to exfiltrate from that job's token/secret scope. (https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

**Pitfalls that must be avoided, per the same GitHub doc:**

1. **`pull_request_target` + checkout of the untrusted ref = secret/token exposure risk ("pwn request").** The doc states the risk is not triggered by `pull_request_target` alone, but by a workflow author overriding the safe default: "`pull_request_target` makes one critical and subtle change: the workflow, and any subsequent `actions/checkout` call that does not specify a `ref`, is taken from the **base repository's default branch**, not from the pull request... You introduce risk when a workflow author overrides this default to run the fork's code," e.g. `actions/checkout@v6` with `ref: ${{ github.event.pull_request.head.sha }}`, followed by a step that executes anything from the checked-out tree (even indirectly, via `make test` running an attacker-controlled Makefile). GitHub names this pattern explicitly: "This pattern is known as a **'pwn request'** and has been the root cause of multiple supply-chain compromises," citing GitHub Security Lab's "Preventing pwn requests." Other vulnerable shapes documented: setting `repository:` to the fork, or fetching PR code via `git fetch`/`gh pr checkout`/downloaded artifacts and then running it — and the doc notes this class of bug is "not unique to `pull_request_target`": any event that runs with secrets and executes fork-controlled code is vulnerable the same way (e.g., a `workflow_run` consuming an untrusted artifact). GitHub further notes it is rolling out a **default policy that blocks `pull_request_target` entirely in public repositories** unless explicitly allowed, currently in an "evaluate" (non-blocking) mode ahead of enforcement on 2026-12-02. (https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

2. **Putting untrusted PR content directly into `run:` shell interpolation = script injection risk.** GitHub's "Secure use reference" documents this as "Good practices for mitigating script injection attacks": any `${{ ... }}` expression sourced from attacker-controlled context (PR title, branch name, commit message, etc.) that is interpolated directly into a `run:` block is injectable, because the expression is substituted **before** the shell script is generated/parsed. GitHub's two recommended mitigations: (a) **pass the value into a dedicated action as an input argument** instead of interpolating it into a shell string (not subject to shell re-interpretation), or (b) for inline scripts, **assign the expression to an intermediate environment variable first** (`env: TITLE: ${{ github.event.pull_request.title }}`) and reference `$TITLE` inside the script body, so the untrusted value is only ever treated as string data, never as script text to be parsed — GitHub's own example shows an attempted injection payload (`a"; ls $GITHUB_WORKSPACE"`) failing harmlessly under this pattern. (https://docs.github.com/en/actions/reference/security/secure-use)

3. **Secrets should never be plain-text/structured blobs even when legitimately used**, per the same "Secure use" doc: "Never use structured data as a secret... do not use a blob of JSON, XML, or YAML... as this significantly reduces the probability the secrets will be properly redacted" from logs — relevant if bcgov's scanner job ever needs any credential (e.g., for a private rule-pack mirror), reinforcing the broader goal of keeping the PR-content-scanning job entirely secret-free and read-only. (https://docs.github.com/en/actions/reference/security/secure-use)

**Practical implication for bcgov/agent-marketplace:** Given the repo's current policy (per `docs/MARKETPLACE_RUNBOOK.md`) that only bcgov org members with push access may open PRs — i.e., anonymous fork PRs currently "fail closed" and are not accepted — the marginal risk from (1) is already structurally mitigated at the contribution-model level, independent of workflow design. However, the GitHub-documented pattern above remains the correct general-purpose design if/when the project ever opens contributions to public forks: run the scanner job on the plain `pull_request` trigger (never `pull_request_target`), do not request any non-default token permissions, do not pass any repository secrets into that job, and ensure any PR-derived strings used in `run:` steps go through an intermediate `env:` variable rather than direct `${{ }}` interpolation into the shell command.

## 5. Final Recommendation

**Primary, required, fail-closed gate (deterministic, offline, no API keys):**

- **Signature/secret layer — gitleaks** (MIT, https://github.com/gitleaks/gitleaks). Run against every changed file in `skills/`, `prompts/`, `instructions/`, `agents/` with a locally vendored `.gitleaks.toml` (no `GITLEAKS_CONFIG` pulled from a remote URL). Use `--exit-code 1` and `-f json`/`-f sarif` so the check is a binary pass/fail with machine-readable findings that match the repo's existing "scanner findings" language. This directly covers secrets/credentials and, with custom rules added to the vendored config, can be extended to flag base64/hex-looking blobs and known dangerous-capability keywords (`curl`, `eval(`, `subprocess`, exfil-shaped URLs) as additional regex signatures.
- **Pattern layer — semgrep generic mode, locally vendored rules only** (LGPL-2.1, https://github.com/semgrep/semgrep). Use custom `languages: [generic]` rules checked into the repo (never pulling from the Semgrep Registry, and run with `--metrics=off`/no registry config, and ideally `--enable-version-check=false`) to add multi-line/structural pattern checks beyond plain regex — e.g., detecting suspicious instruction-override phrasing patterns or known prompt-injection scaffolding across a few lines — while being explicit in rule comments that generic mode cannot decode obfuscated/encoded text, so obfuscation detection (zero-width characters, unusual unicode categories, base64/hex envelopes) should be implemented as a dedicated, simple deterministic pre-processing/normalization step (e.g., a small first-party script that flags non-ASCII control/format characters and high-entropy encoded blocks) feeding structured findings into the policy layer below, rather than relying on semgrep itself to "see through" obfuscation.
- **Policy/gating layer — OPA/Conftest** (Apache-2.0, https://www.conftest.dev/, https://www.openpolicyagent.org/docs). Convert gitleaks/semgrep/custom-scanner findings plus the asset's manifest/frontmatter (declared capabilities, lifecycle state, allow-listed exceptions) into a single structured JSON "input" document, then express the actual merge-blocking decision as versioned `.rego` policy (`deny`/`violation` rules) reviewed through normal PR history — matching and formalizing bcgov's existing "deterministic security policy" / "policy-version" / "fails closed" vocabulary, and giving a clean separation between *detection* (gitleaks/semgrep/custom) and *policy* (what is blocking vs. advisory, what requires CODEOWNER override).

This three-layer combination (signature scanner → pattern/structural scanner → policy engine) is fully local, requires no API keys or egress, and produces a deterministic, machine-checkable pass/fail exit code suitable as a required GitHub Actions status check, consistent with the repo's current "no-network," "fails closed" design.

**Where a secondary/optional LLM-classifier signal could fit:** Not as a blocking check. If desired, a classifier-based scanner (e.g., a locally-run ML model equivalent to llm-guard's `PromptInjection`/`Toxicity` scanners, bearing in mind llm-guard itself is archived/unmaintained per https://github.com/protectai/llm-guard, or a cloud API such as Microsoft Prompt Shields https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection) could run as a **non-blocking, advisory** workflow step that posts a PR comment or review annotation ("heuristic classifier flagged possible injected instructions — human review recommended") without affecting the required status check's exit code. This keeps the deterministic gate's guarantees (reproducible, auditable, offline) intact while still giving human CODEOWNER reviewers an extra, clearly-labeled-as-probabilistic data point for novel phrasing that static rules have not yet been written to catch. Tools in this category that depend on third-party API keys (Rebuff's OpenAI/Pinecone requirement, Prompt Shields' Azure dependency) should never be wired into a path that is required for merge, since a vendor outage or missing credential would either block all merges (violating "fails closed" in the wrong direction — denial of service rather than security) or silently no-op depending on implementation, either of which undermines the reproducibility bcgov's docs require.
