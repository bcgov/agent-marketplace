# Safe fork-PR validation and auto-merge for `bcgov/agent-marketplace`

Findings for [issue #10](https://github.com/bcgov/agent-marketplace/issues/10), researched 2026-10-30. GitHub platform claims cite GitHub's own documentation or Security Lab; repository observations cite its files and public GitHub API. This is a design, not an implementation or confirmation of private organization settings.

## Trust boundaries and fork validation

| Event | Workflow and checkout context | Fork credentials | Appropriate use |
| --- | --- | --- | --- |
| `pull_request` | PR merge commit, including contributor-controlled workflow/code | Fork runs receive read-only `GITHUB_TOKEN`, no other secrets; first-time contributors may need a maintainer to approve the run | Build/test/scan fork content, **without secrets or write privileges**. |
| `pull_request_target` | Base branch's trusted workflow and default checkout | Base repository token and secrets are available, subject to declared permissions and event policy | Metadata-only triage, membership lookups and API writes; **never execute fork code**. |
| `workflow_run` | Subsequent workflow on default branch, after a named CI workflow completes | Privileged workflow can receive secrets/write token | Separate read-only fork CI from a trusted API-only decision job; treat downloaded artifacts and metadata as attacker-controlled. |

Sources: [event semantics and fork permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request), [`pull_request_target` security](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target), [`workflow_run` security warning](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), [approving fork runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks).

**Pwn request:** A privileged `pull_request_target` job that checks out the PR head (`ref: ${{ github.event.pull_request.head.sha }}`), or a privileged `workflow_run` job that downloads a fork-produced artifact, becomes exploitable if it *executes* that content (`uv run`, `pip install`, a build script, shell interpolation, etc.). Avoid running untrusted inputs in privileged jobs; validate identifiers and API responses, pin third-party actions, restrict job permissions, and do not assume artifacts or caches are trustworthy. [GitHub Security Lab's pwn-request analysis](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/); [GitHub's current `pull_request_target` guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

**Upcoming policy:** GitHub's [default Actions event policy](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#default-policy-for-pull_request_target) blocks `pull_request_target` in public repositories without another applicable event policy; its documented evaluation period ends **2026-12-02** for affected repositories. Confirm whether bcgov explicitly allows this event before choosing that design. `workflow_run` avoids that particular event-policy dependency, not the underlying pwn-request risk. [GitHub policy documentation](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#default-policy-for-pull_request_target).

## Author membership: use a separate credential, fail closed

The workflow `GITHUB_TOKEN` is a repository-scoped installation token, **not an org membership credential**; a fork's `pull_request` run also cannot receive `ORG_READ_TOKEN` from secrets. [GitHub token scope](https://docs.github.com/en/actions/concepts/security/github_token); [fork restrictions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request). `GET /orgs/bcgov/public_members/{login}` only checks *public* membership and is insufficient for private members. For the real gate use `GET /orgs/bcgov/memberships/{login}` and require `state: active` (an invited/pending user must not pass), or `GET /orgs/bcgov/members/{login}` for active member existence. Organization-scoped **Members: read** permission is needed for an installation/fine-grained token; a classic PAT from an org member needs `read:org` and applicable SSO authorization. A 404 can mean absent membership **or inadequate visibility**, so treat it as unverified, never as proof of external status. [GitHub REST org-member endpoints, token permissions and response fields](https://docs.github.com/en/rest/orgs/members?apiVersion=2022-11-28).

Prefer an org-installed **GitHub App** with `Members: read`, and separate minimal repository write permissions for the privileged decision/merge job. Mint a short-lived installation token in trusted code (GitHub documents [`actions/create-github-app-token`](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow)); do not expose its private key or token to fork code, untrusted actions, logs or artifacts. A PAT can work but belongs to a human account, needs lifecycle/SSO handling, and broadens credential risk. `GITHUB_TOKEN` alone does not solve org membership. [GitHub's guidance on additional permissions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token); [GitHub App authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow).

## Enforcement: checks, reviews, bypass, and queue

[Rulesets layer with branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets); the strictest applicable rules apply. Native [auto-merge](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request) waits for **all required checks and reviews**, not merely deterministic scans; write permission is needed to enable it. Changes pushed by a contributor without write access disable auto-merge, but a bot should also re-check current head/base and gate outcome before acting. A [merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) also waits for requirements; required Actions checks must trigger on `merge_group` and validate the queue's synthetic ref. Neither auto-merge nor merge queue bypasses required human approvals.

A [ruleset bypass actor](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository#granting-bypass-permissions-for-your-branch-or-tag-ruleset) can be a GitHub App, with **for pull requests only** preferable to unrestricted bypass. Bypass must be narrowly assigned and the App must enforce all desired conditions itself: it can also bypass required checks, signed commits, CodeQL, or specialty reviews if its logic is wrong. Use a distinct bot identity from any general-purpose publishing token; do not grant bypass to a workflow that processes arbitrary contributor code. [PR review API](https://docs.github.com/en/rest/pulls/reviews?apiVersion=2022-11-28#create-a-review-for-a-pull-request) permits an authorized App to submit a review, but official documentation does **not** establish that an arbitrary App approval satisfies this repository's required human review; do not assume it does or use it as a substitute for specialty CODEOWNERS approval. [Protected branch review requirements](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

[CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) uses the **base branch** file and last matching pattern; a line with no owner clears an earlier catch-all. A PR touching only ownerless paths will not require a *code-owner* review, **but any separately required minimum approval still applies**. A PR that touches any owned path must still get the matching owner's review. Teams must be visible and have repository write access. Validate file patterns with realistic mixed-path PRs rather than assuming a directory rule covers every modified file.

## Observed repository/bcgov settings (public, checked 2026-10-30)

- [`.github/workflows/pr.yml`](../.github/workflows/pr.yml) currently hard-fails all forks in `fork-gate`; `lint-tests`, `skills`, `marketplace` run after that gate; `results` aggregates their outcomes. Removing the fork gate safely requires scrutinizing the rest of the workflow and keeping fork jobs read-only. [`.github/workflows/community-intake.yml`](../.github/workflows/community-intake.yml) runs on `pull_request`, attempts the org-membership call with `ORG_READ_TOKEN || github.token`, computes account-age/velocity signals and runs `marketplace.py intake`; fork PRs cannot obtain the secret and thus cannot pass this gate as currently built. It also labels PRs (writes) and therefore needs a separate trusted stage for fork intake.
- [`.github/CODEOWNERS`](../.github/CODEOWNERS) starts with `* @bcgov/agent-marketplace-maintainers`, clears ownership for community asset namespaces, then assigns `@bcgov/security` for security specialty assets. [Config](../config/marketplace.yaml) requires org membership, a 30-day account-age proxy, max 3 open submissions, and risk ceiling `elevated`. **Auto-publish means merge after passing policy, not merely labeling a PR eligible**; non-community or mixed-path changes must never inherit community eligibility.
- The publicly readable active [main protection ruleset (REST API)](https://api.github.com/repos/bcgov/agent-marketplace/rulesets/24379494) targets the default branch and requires **1 approving review**, code-owner approval, extra approval for unattributed changes, resolved conversations, `results` status check (strict/up to date), signed commits, and CodeQL (`errors` / `high_or_higher` thresholds); deletion and non-fast-forward are blocked. Its visible bypass list is a DeployKey and a RepositoryRole actor (ID 5), **not a dedicated App**. [Repo settings API](https://api.github.com/repos/bcgov/agent-marketplace) reports `allow_auto_merge: true` and squash merge enabled. The [legacy branch protection API](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection) returns 404 for `main` here: protection is the ruleset, not a classic rule. Therefore **ownerless community paths currently still cannot auto-merge without one approval or an expressly configured bypass/change to rules**. Specialty paths require their matching owner as well as the global review, and a bot bypass that ignores this would violate product intent.
- Repository Actions permissions are publicly readable and report enabled/all actions ([repo Actions permissions API](https://docs.github.com/en/rest/actions/permissions#get-github-actions-permissions-for-a-repository)); the org Actions permissions endpoint returned **403** for the available credentials, so org/enterprise event policy, fork-run approval policy, App installation/SSO, and org-level rulesets remain **unverified**. Ask bcgov admins to inspect Settings → Actions and Rulesets, particularly the December 2026 `pull_request_target` policy. Do not equate public repo settings with org permission to execute privileged workflows.

## Recommendation: two architectures

**A — Read-only fork CI + trusted `workflow_run` policy engine (preferred).** Remove fork-gate; run existing scans on `pull_request` with `contents: read` and no secrets, and make `results` fail for any missing/failed scan. Where possible keep all deterministic policy from the protected base branch (or explicitly reject fork edits to policy files); untrusted PR workflow modifications must not be able to forge the required `results` check. A separate base-branch `workflow_run` job triggered on *successful* `PR` completion uses the org-installed App only after verifying the upstream repository/workflow identity, event, PR number, current base/head SHA and fresh required checks through the GitHub API. **Do not trust fork-provided artifacts as evidence or execute them.** Compute author membership and policy from trusted code against a validated exact commit/diff; fail closed on API errors, policy-file changes, mixed specialty/tooling paths, held/risky decisions or stale heads. Publish a dedicated policy check (pin its issuing App in the ruleset) and enable auto-merge only when requirements are met. To achieve *zero human approvals* for eligible community-only PRs under today's ruleset, admins must either (1) create a narrowly scoped App **PR-only bypass** and let that App merge *only* after independently enforcing all required checks/CodeQL/signature rules and verifying no owned paths, or (2) change global review requirements in a way that still guarantees specialty CODEOWNERS review. Native auto-merge on its own **cannot satisfy the current 1-review rule**. Trade-off: safer separation and not subject to `pull_request_target` default policy; more API/state coordination, and bypass is a high-impact control requiring a rigorous trusted gate.

**B — Read-only fork CI + metadata-only `pull_request_target` coordinator.** Same validation/requirements as A, but run privileged author and path checks on `pull_request_target` with **no checkout of PR content, no PR code execution and no fork-controlled shell interpolation**; use GitHub APIs and base-branch policy code only. Subject to bcgov org event policy and possible December 2026 event block. Simpler event-to-PR linkage; still requires a scoped App, the admin ruleset change/bypass, and revalidation after synchronize/reopen/rebase. In both options, keep a separate human-reviewed specialty path, never permit mixed PRs to claim community-only eligibility, and test fork, force-push, missing-check, and policy-edit cases before enabling automated merges.
